# 关键变动：从全局位移量到 chunk-scoped 定位体系

> **重构日期**：2026年9月20日  
> **重构范围**：validate-s0-quality.js, recall-nouns-llm.js, s1-llm-fill.js, merge-s0-s1.js  
> **重构目标**：彻底去除全局 fullText 拼接，改为 chunk 级别独立处理 + chunkKey 直接绑定

---

## 一、重构动机

### 旧版架构的核心问题

所有脚本都依赖一个共同的设计缺陷：**构建全局 fullText 字符串，用换行符 `\n` 拼接所有 chunk**。

```javascript
// ❌ 旧版：全局拼接
function buildPureTextTable(bookIndex) {
  let offset = 0;
  for (const chunk of bookIndex.chunks) {
    const text = atomSearchText(chunk).trim();
    entries.push({ chunkKey: chunk.key, startOffset: offset, endOffset: offset + text.length });
    offset = endOffset + 1; // +1 跳过换行符 \n
  }
  const fullText = entries.map(e => e.text).join('\n'); // ⚠️ 全局拼接
  return { fullText, entries };
}
```

**导致的问题链**：

1. **内存开销大**：605 个 chunk 拼接成单个百万字符级字符串
2. **位移量脆弱**：三个脚本各自调用 `buildPureTextTable`，只要有一处清洗逻辑不一致（比如 `atomSearchText` 改了空白符处理规则），全局位移就会错位
3. **跨 chunk 匹配风险**：名词可能跨越 chunk 边界（chunk1 结尾 + `\n` + chunk2 开头），造成误匹配
4. **O(n) 反查**：每次通过全局位移定位 chunk，需要线性扫描 `entries` 数组
5. **无法并发**：spaCy 处理必须按全局顺序，无法按 chunk 并发调用
6. **数据结构冗余**：输出的 JSON（如 `s0-hits.json`、`final-noun-index.json`）只有 `{start, end}`，不带 `chunkKey`，后续任何使用都要重新反查

---

## 二、重构后的新架构

### 核心原则：chunk 是第一公民

```javascript
// ✅ 新版：chunk-scoped 处理
const chunkByKey = new Map(chunks.map(c => [c.key, c])); // O(1) 查找

// 每个 chunk 独立处理，spaCy 结果直接标记 chunkKey
async function processChunk(chunk) {
  const text = atomSearchText(chunk);
  const spacyResult = await callSpacyAPI(text);
  
  return spacyResult.nouns.map(noun => ({
    surface: noun.surface,
    chunkKey: chunk.key,        // ✅ 直接绑定
    localStart: noun.start,     // ✅ 相对于该 chunk 的局部位移
    localEnd: noun.end,
    page: chunk.page
  }));
}
```

## 三、逐文件对比

### 1. validate-s0-quality.js

#### 改前（全局处理）
```javascript
// ❌ 一次性构建全局 fullText
const pureTextTable = buildPureTextTable(bookIndex);
const fullText = pureTextTable.fullText;

// ❌ 一次性调用 spaCy 处理全文
const spacyRes = await fetch(SPACY_URL, {
  body: JSON.stringify({ text: fullText })
});

// ❌ 输出只有全局位移，无 chunkKey
const s0HitsOutput = {
  hits: hits.map(h => ({ surface: h.surface, start: h.start, end: h.end }))
};
```

#### 改后（chunk 级别处理）
```javascript
// ✅ 构建 chunkKey → chunk 的 Map（O(1) 查找）
const chunkByKey = new Map(chunks.map(c => [c.key, c]));

// ✅ 并发处理每个 chunk
const chunkResults = await processBatch(chunks, async (chunk) => {
  const text = atomSearchText(chunk);
  const spacyResult = await callSpacyAPI(text);
  return { chunkKey: chunk.key, nouns: spacyResult.nouns };
}, 10); // 并发度 10

// ✅ 输出带 chunkKey
const s0HitsOutput = {
  hitsByChunk: chunkResults.map(r => ({
    chunkKey: r.chunkKey,
    nouns: r.nouns.map(n => ({
      surface: n.surface,
      localStart: n.start,  // ✅ 局部位移
      localEnd: n.end
    }))
  }))
};
```

**关键改进**：
- 无需全局拼接，内存占用降低
- spaCy 并发调用（原来串行），性能提升 ~10 倍
- 输出直接标记 chunkKey，无需后续反查

### 2. recall-nouns-llm.js

#### 改前（全局位移反查）
```javascript
// ❌ 构建全局 fullText
const { fullText, entries } = pureTextTableByBookKey[bookKey];

// ❌ 在全局 fullText 中搜索名词
const idx = fullText.indexOf(noun.surface, truncPos);

// ❌ 通过全局位移反查 chunk（O(n) 线性扫描）
const entry = entries.find(e => idx >= e.startOffset && idx < e.endOffset);

return {
  chunkKey: entry.chunkKey,
  offset: idx  // ❌ 全局位移
};
```

#### 改后（chunk-scoped 搜索）
```javascript
// ✅ 直接用 chunkKey 查找（O(1)）
const chunk = chunkByKey.get(chunkKey);
const text = atomSearchText(chunk);

// ✅ 仅在该 chunk 内搜索（从 localTruncPos 开始）
const localIdx = text.indexOf(noun.surface, localTruncPos);

return {
  chunkKey,
  localOffset: localIdx,  // ✅ 局部位移
  page: chunk.page
};
```

**关键改进**：
- 搜索范围从百万字符降到单个 chunk（通常几百字符）
- O(1) Map 查找替代 O(n) 线性扫描
- 无跨 chunk 匹配风险

### 3. s1-llm-fill.js

#### 改前（全局 fullText 上下文窗口）
```javascript
// ❌ 重新构建全局 fullText
const pureTextTable = buildPureTextTable(bookIndex);
const fullText = pureTextTable.fullText;

// ❌ 从 missedNounSamples 读取截断（只有全局 start/end，无 chunkKey）
const truncations = report.missedNounSamples; // [{start: 12345, text: "..."}]

// ❌ 在全局 fullText 里搜索，用上下文窗口 ±50 字符
const searchStart = Math.max(0, truncStart - 50);
const searchEnd = Math.min(fullText.length, truncEnd + 50);
const searchRegion = fullText.slice(searchStart, searchEnd);

// ❌ 找不到就退化成全文搜索（误匹配风险最高）
if (offsets.length === 0) {
  let at = fullText.indexOf(noun, 0);
  // ...全文扫描
}
```

#### 改后（chunk-scoped 窗口搜索）
```javascript
// ✅ missedNounSamples 现在带 chunkKey
const truncations = report.missedNounSamples; // [{chunkKey: "h1.xxx", localStart: 123, text: "..."}]

// ✅ 直接定位到该 chunk
const chunk = chunkByKey.get(truncation.chunkKey);
const chunkText = atomSearchText(chunk);

// ✅ 在该 chunk 内搜索（局部上下文窗口）
const searchStart = Math.max(0, truncation.localStart - 50);
const searchEnd = Math.min(chunkText.length, truncation.localEnd + 50);
const searchRegion = chunkText.slice(searchStart, searchEnd);

// ✅ 找不到也只在该 chunk 内兜底，不会跨 chunk
if (offsets.length === 0) {
  let at = chunkText.indexOf(noun, 0);
  // ...仅限该 chunk
}
```

**关键改进**：
- 不再重复构建全局 fullText（三处脚本各自构建的问题彻底消失）
- 上下文窗口精准（chunk 内），不会跨 chunk 污染
- 兜底搜索范围限制在单个 chunk，误匹配风险降低

### 4. merge-s0-s1.js

#### 改前（全局位移去重）
```javascript
// ❌ 一次性调用 spaCy 处理全文
const spacyRes = await fetch(SPACY_URL, {
  body: JSON.stringify({ text: fullText })
});

// ❌ offsets 只存全局位移
mergedNouns.get(id).offsets.push({ start: token.start, end: token.end });

// ❌ 去重 key 依赖全局位移
unique.set(`${off.start}-${off.end}`, off);
```

#### 改后（chunkKey + 局部位移去重）
```javascript
// ✅ 并发处理每个 chunk
const chunkResults = await processBatch(chunks, processChunk, 10);

// ✅ offsets 带 chunkKey + 局部位移
mergedNouns.get(id).offsets.push({
  chunkKey: chunk.key,
  localStart: noun.start,
  localEnd: noun.end,
  page: chunk.page
});

// ✅ 去重 key 用 chunkKey + 局部位移
unique.set(`${off.chunkKey}:${off.localStart}-${off.localEnd}`, off);
```

**关键改进**：
- 并发调用 spaCy（原来串行），速度提升
- 去重 key 更精准（同一个词在不同 chunk 的不同位置可以区分）
- 输出的 `final-noun-index.json` 可以直接使用，无需反查

## 四、数据结构变化

### 旧版输出（s0-hits.json / final-noun-index.json）
```json
{
  "nouns": [
    {
      "id": "socrate",
      "surface": "Socrate",
      "offsets": [
        {"start": 123456, "end": 123463},
        {"start": 234567, "end": 234574}
      ]
    }
  ]
}
```
**问题**：只有全局位移，不知道属于哪个 chunk，后续使用必须重新调用 `buildPureTextTable` 反查。

---

### 新版输出
```json
{
  "nouns": [
    {
      "id": "socrate",
      "surface": "Socrate",
      "offsets": [
        {
          "chunkKey": "h1.ciDEXNZIEN2h0eBjV0zU_...",
          "localStart": 234,
          "localEnd": 241,
          "page": 25
        },
        {
          "chunkKey": "h1.i6CcOy0giLJLPz8G-1he...",
          "localStart": 15,
          "localEnd": 22,
          "page": 87
        }
      ]
    }
  ]
}
```
**优点**：
- 直接包含 chunkKey，可以立即查找原始 chunk
- 局部位移精准，不依赖全局拼接
- 同一个词在不同 chunk 的不同位置可以精确区分

## 五、性能与可维护性对比

| 维度 | 改前 | 改后 |
|------|------|------|
| **内存占用** | 百万字符级 fullText | 单个 chunk KB 级 |
| **spaCy 调用** | 串行（或大批次） | 并发（10 个/批次） |
| **chunk 定位** | O(n) 线性扫描 | O(1) Map 查找 |
| **位移量精度** | 三处脚本逻辑必须一致 | 每个 chunk 独立，互不影响 |
| **跨 chunk 风险** | 存在（拼接符 `\n`） | 不存在 |
| **代码耦合** | 高（全局 fullText 构建逻辑） | 低（chunk 独立处理） |
| **输出数据** | 需二次反查 | 直接可用 |
| **错误传播** | 一处错全局错 | chunk 隔离，错误不传播 |

## 七、总结

这次重构彻底解决了"全局 fullText 拼接"的根本缺陷，将位移量体系从**全局绝对位置**改为**chunk-scoped 相对位置 + chunkKey 直接绑定**。

**核心收益**：
1. **精度提升**：chunk 内搜索，无跨 chunk 误匹配
2. **性能提升**：O(1) 查找 + spaCy 并发调用
3. **可维护性提升**：chunk 独立，错误不传播
4. **数据结构简化**：输出直接可用，无需二次反查

**代价**：
- 输出 JSON 文件体积略增（每个 offset 多存 `chunkKey` 字段）
- 下游代码需要适配新的数据结构

**结论**：这是一次必要的、收益远大于代价的架构重构。
